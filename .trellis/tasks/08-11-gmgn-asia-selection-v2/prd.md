# 完善 GMGN 亚洲节点选拔与订阅发布

## Goal

建立一条面向 Clash Verge 手动选择的可靠节点供应链：GitHub 尽可能收集新鲜、独立的香港、日本、韩国、新加坡、台湾候选；CNB 中国 Runner 对全部候选执行覆盖时间窗口的 GMGN 20 轮测速；发布严格主力、亚洲候补和清晰的地区分组，同时避免亚洲节点因一次或一轮异常永久消失。

用户价值不是“自动选出一个永远最快的节点”，而是缩小手动测速范围，并保留可能因 CNB 出口差异而在用户本地仍然好用的亚洲节点。

## Background and Confirmed Facts

- 用户在 Clash Verge 中通常手动测速并手动选择节点，不依赖自动选择。
- Clash 的体验标准是访问 `https://gmgn.ai/` 时延迟不超过 1000 ms；超过 1000 ms 的轮次不应算合格。
- GitHub 侧职责已经确定为扩大候选池，不应用单轮 GMGN Timeout 直接剔除亚洲候选。
- CNB 侧职责已经确定为对完整候选集执行 GMGN 20 轮深度选拔，并尽可能利用分片和并发缩短总耗时。
- CNB 架构已经确定为“协调器 → 多个独立 Mihomo 测速分片 → 完整性校验 → 汇总发布”；不同节点尽量并行，同一节点的 20 轮保持时间顺序，不能同时发出。
- 80 是期望容量，150 是硬上限；质量不足时允许少于 80，禁止为凑数降低主力标准。
- 非亚洲只保留最稳定的约 10–20 个；高质量亚洲节点可以占据更多名额。
- 当前公开产物同时存在：GitHub 全候选池、旧 gstatic CNB 订阅、新 GMGN CNB 订阅。旧订阅不会因刷新自动迁移到新分支。
- 当前 GMGN 正式订阅已能完成四分片、20 轮、失败保护和独立发布，但真实出口地区、完整历史保护、出口多样性和地区分组尚未完整实现。
- `ASIA-KEEP KR 012` 证明 CNB 与用户本地出口可能得出不同结论：它在用户本地 GMGN 测速可低至约 80 ms，但没有达到本轮 CNB GMGN 主力/弹性门槛。
- 规划审计发现 Trellis 曾把 `manager` 子模块误设为默认包；现已将根包 `aggregator` 设为默认并补齐真实流水线规范，后续子任务必须继续加载该规范，不能回退到 `manager`。
- 2026-08-11 线上固定快照包含 2260 个候选，名称启发式判定亚洲 1163 个；四分片合计完成 45200 次尝试，分片耗时约 23–24 分钟，证明当前四分片方案在该规模下可运行。
- 同一快照中，1163 个名称亚洲候选里有 74 个至少得到一次 GMGN 响应、37 个至少一次 `<=1000 ms`、17 个达到 `>=10/20`；当前正式 GMGN 输出仅 26 个（亚洲 17、非亚洲 9）。这说明“严格主力”和“供用户手动复测的亚洲候补”必须是两个不同层级。
- 当前一次“观察保留”并不是真正的跨运行保留：它只读取上一版分组，低于 10/20 会立即消失，且公开 shadow/output 分支每次强制改写为单一快照，无法支撑连续 2–3 次差评后再删除。
- 当前 runner 被观测为中国广东，但工作流只选择 AMD64 runner；出口国家/省份目前是遥测信息，不是发布前置条件，也没有逐分片出口一致性校验。
- 当前 GMGN 发布器只接收节点汇总，无法读取全局 403/429/Timeout/控制器错误趋势；本次 45200 次尝试中 38809 次无结果，发布器仍无法判断这是候选质量差还是 runner/目标的系统性异常。
- 当前 GMGN 输入是 GitHub 已发布的 `clash-verge-output`，不是原始爬取全集；该输出已丢失节点来源归属，并存在大量共享服务器/端点的别名，后续无法直接执行来源和故障域多样性约束。
- 早期讨论过按“数学上不可能达标”提前结束节点，但后续已经明确正式运行必须为每个固定快照候选留下完整 20 轮观测，并需要候补/历史状态；因此正式 GMGN 选拔不采用会产生少于 20 次观测的提前淘汰。
- 用户已确认亚洲手动候补边界：新亚洲节点本轮只要至少得到一次 GMGN 响应，即使所有响应都超过 1000 ms，也可进入明确标注的手动候补；`<=1000 ms` 次数只决定核心/弹性主力等级。新出现且 20 轮完全无响应的节点只保留在 GitHub 全候选池。
- 用户进一步确认亚洲策略可以宽松：亚洲候补的目标是保留给用户本地手动复测的可能性，不因 CNB 侧出口/IP/ASN 重复或单次慢响应直接删除；非亚洲仍执行严格质量和数量限制。
- 用户确认不需要以节省 CNB 资源为目标，正式 GMGN 深测应优先保证新鲜度：GitHub 每次发布新的候选 profile SHA 后都自动触发一次 CNB 20 轮运行，同一 SHA 不重复运行，手动触发仍可保留。
- 用户确认旧 gstatic 生命周期：新 GMGN 方案完成连续 3 次有效影子验收并切换推荐入口后，停止 gstatic 自动更新；不删除 `clash-cn-output`，保留最后一版并明确标记为冻结旧版备用。未来只有 GMGN 长期不可用时才手动恢复该流水线。

## Requirements

### R1. GitHub 候选池职责

- 持续聚合尽可能多的新鲜代理来源，重点扩大香港、日本、韩国、新加坡、台湾候选。
- 候选池不得因单轮 GMGN Timeout 或一次网络抖动删除亚洲节点。
- 对完全重复配置做确定性去重，同时保留来源、协议、服务器和地区标签等可用于后续多样性判断的元数据。
- 状态文件必须公开来源数量、候选数量、亚洲候选数量、去重数量、数据时间和配置摘要，且不得泄露额外凭据。
- GitHub 候选订阅与 CNB 正式优选订阅的名称和文档必须明确区分，避免用户把候选池误认为最终优选结果。
- GitHub 发布保护不能只看总节点数；必须同时检查亚洲总量、HK/JP/KR/SG/TW 单区数量、来源 quorum 和相对保留比例。单个固定源暂时失败或某地区异常归零时，不得用缩水版覆盖 last-good 候选池。
- 固定 raw 源必须有逐源 last-success 快照、新鲜度、掉量和恢复状态；精确重复配置需要合并全部 provenance 和亚洲保护证据，而不是只保留字典序最先出现的名称。
- 机场/订阅探索必须给 known-good、未尝试和到期重试来源分别预留配额，避免已知成功站点填满 192 个运行名额后让新来源长期饥饿。
- 新外部源按边际增益接入：记录原始数量、精确唯一数、唯一入口数、与现池重叠、五地区数量、最后更新时间和生成/验证透明度；不得把数千条高度重复聚合源无上限直接送入 CNB。
- 亚洲识别应补齐常见机场代码等安全别名，并用测试防止短词误判；未被名称识别的真实亚洲节点不应因识别表缺口永久落入非亚洲单轮严格过滤。
- 外部代理配置按不可信输入处理：只允许 Mihomo 支持且项目明确接受的字段/协议，拒绝把 loopback、link-local、私网或云元数据地址作为代理服务器；解析/测速阶段不得持有正式分支写凭据或私有订阅 secrets，发布阶段只消费经过校验的固定快照与结果。
- HMAC identity producer/validator 必须是独立受控阶段，只消费已安全清洗的固定 snapshot/fixture，不执行订阅发现或 Mihomo 探测；HMAC key、发布 token 和不可信原始来源不得同时出现在一个处理阶段。
- 私有订阅 URL、token、来源凭据和可逆来源标识不得进入公开 provenance；若启用手动私有订阅，是否允许公开其派生代理必须使用显式配置，不能隐式继承公开发布行为。

### R2. CNB GMGN 20 轮完整测速

- 每次正式选拔必须对本次固定快照中的全部候选执行恰好 20 轮，不使用一次性预检淘汰候选。
- 测速目标固定为 `https://gmgn.ai/`，HTTP 期望状态为 200。
- 单轮 `<=1000 ms` 才记为达标；请求可以保留更高的网络等待上限，以区分慢响应和无结果，但超过 1000 ms 不能算通过。
- 20 轮必须覆盖版本化的最短观察窗口，初始值为每节点首末采样至少 900 秒，避免在瞬时网络状态下快速完成；后续只能依据影子证据通过策略版本显式调整。
- 每轮必须记录实际开始/结束时间；对同一节点的首末采样间隔必须达到版本化最短观察窗口。不同分片开始时间可以略有错开，但不能导致某个分片只覆盖瞬时状态。
- 所有候选必须恰好分配到一个分片；所有分片必须使用同一来源 SHA、主分支 SHA、阈值和轮数。
- 充分使用 CNB 可用 CPU、并发和并行任务，但并发策略不得导致明显自限流或破坏 20 轮可比性。
- 每个分片必须使用独立 Mihomo 进程、控制端口、工作目录和日志；候选按稳定 HMAC `candidate_id` 确定性均衡分片，并允许分片错峰启动以降低瞬时连接峰值。
- 并发度需要通过真实错误率和吞吐量自动/离线标定，目标是最快的可靠并发，而不是固定追求 32–48 workers；提高并发若显著增加 Timeout、控制器 5xx 或对照请求失败，必须回退。
- 每个新的 GitHub 候选 profile SHA 应触发一次且仅一次正式 GMGN 运行；任务锁负责排队或拒绝重复，同一 SHA 的重试只能用于基础设施失败恢复，不能重复累加节点 bad-run streak。

### R3. 完整且可解释的测速统计

- 每节点至少记录：20 轮尝试数、`<=1000 ms` 次数、`>1000 ms` 响应次数、无结果次数、错误类型统计、中位数、P90、最小/最大延迟、抖动、前后半程和分块达标次数。
- Timeout、HTTP 403、HTTP 429、控制器错误、连接失败和其他无结果不得在 P90 或总评分中“消失”。
- 排名第一关键字为 `<=1000 ms` 次数，其次才是响应数、P90、中位数和抖动。
- 公共诊断必须脱敏，但应能解释某个公开节点为何入选、降级或淘汰；不能再次出现只能推断、无法定位具体节点 20 轮结果的情况。
- 公开节点、端点、服务器和出口标识必须使用带版本/identity epoch 的 HMAC opaque ID，不得公开裸配置指纹或可枚举的端点/出口散列；身份密钥或 schema 无法迁移时必须失败关闭。
- GitHub 与 CNB 必须持有相同 HMAC key 字节及相同 `identity_key_version`/`identity_epoch`，并在真实候选处理前通过无凭据固定向量互校；任一端配置漂移时不得发布候选或开始测速。
- 发布选择阶段必须同时接收脱敏的全局轮次趋势和错误分类；当 403/429、全局 Timeout、控制器异常或对照请求异常达到版本化门槛时，应拒绝替换上一版，而不是把系统性事故计为全部节点变差。
- 每个分片应执行不经过候选代理的目标可达性对照，并记录 Mihomo/controller 健康；只有来源、四分片、目标对照和完整性检查全部通过的运行才定义为“有效运行”。
- 四个 probe 分片必须各自记录实际 Runner 出口，并测试同一小组版本化 canary/锚点；出口地区不一致或 canary 延迟/错误率差异超过门槛时，不得把四片直接进行统一排名和发布。

### R4. 亚洲优先、非亚洲严格的分层政策

- 亚洲核心、亚洲弹性和非亚洲稳定使用独立阈值。
- 初始基线沿用已通过真实影子数据验证的策略：亚洲核心 `>=14/20` 且前后十轮各至少 5 次；亚洲弹性 `10–13/20`；非亚洲基础入选 `>=16/20`，扩展名额使用 `>=18/20`。
- 亚洲手动候补包含本轮 `response_count >= 1`、但未达到亚洲弹性门槛的亚洲节点，以及仍处于三次历史保护窗口内的旧亚洲候补。该层不计入主力质量，不进入自动组，也不能被用于宣称达到稳定容量目标。
- 阈值只能根据公开诊断和明确版本修改，不能为达到 80 个临时自动降低。
- 亚洲主力数量不设置低配额；符合质量标准的亚洲节点在 150 总上限内应优先保留。
- 非亚洲总数限制在 10–20 个，并受更严格质量标准约束。
- 当总量未达到 150 时，满足亚洲候补准入的节点不因多样性重复被硬删除；超过 150 时，先保留核心/弹性与历史保护节点，再按响应质量、地区覆盖、出口/ASN/来源集中度裁剪普通亚洲候补。

### R5. 跨运行历史保护与恢复

- 亚洲节点一次异常不得直接从所有面向用户的输出中消失；应降到亚洲候补或观察状态。
- 只有连续 3 次“有效 CNB 正式运行”都低于保留标准时才从候补移除；基础设施异常、来源不完整或拒绝发布的运行不计入这 3 次。
- 高频触发不能让同一短时网络事故快速消耗全部历史保护；连续差评必须来自不同有效来源快照，并受版本化最短计数间隔约束。
- 最短计数间隔只限制坏 streak 增加；新 accepted valid run 只要节点恢复至少一次响应，就应立即清零 streak 并恢复/晋级。间隔不足但 accepted 的新 SHA 仍必须推进 history 顶层 run/source，与 current bundle 保持一致。
- 节点重新达到核心或弹性标准时自动恢复，无需人工编辑名单。
- 来源已经消失、代理配置失效或无法被 Mihomo 加载的节点可以直接移除。
- “来源已经消失”必须与暂时抓取失败区分：单次 HTTP/限流/解析故障只进入来源观察期，不得删除历史节点；只有来源在连续有效 GitHub 采集或配置化时间窗口内都确认缺失，才视为真正消失。
- 历史状态必须使用稳定 HMAC `candidate_id` 而非易变节点名称关联，并保存每次运行的状态迁移原因；裸 fingerprint 不进入公开分支。
- identity key/epoch 轮换不得丢失当前快照外的名称 tombstone：未能重算的新 ID 先保留 legacy ID/epoch，旧 key 只有在 tombstone 完成迁移或经过版本化保留期和可审计 GC 后才能退役。
- 历史必须保存在可跨强制发布继续读取的状态文件中，并至少保留满足移除门槛所需的最近运行窗口；公开 shadow 与正式 profile 必须能按 `run_id` 互相追溯。
- 被判定为基础设施异常、来源不完整或最终拒绝发布的运行不得增加节点的连续差评次数；历史状态、正式 profile 和其对应诊断必须原子关联，避免 profile 保留旧版但诊断已被新版覆盖。

### R6. 真实出口地区和节点多样性

- 最终地区分组不能只依赖节点名称；至少对最终入选及候补节点验证真实出口国家/地区。
- 初始真实出口验证范围确定为：本轮至少得到一次 GMGN 响应的节点、全部严格入选节点及仍在历史保护窗口内的亚洲候补；结果按稳定 HMAC `candidate_id` 缓存并设置可配置 TTL。无需对 2260 个完全无响应的新候选逐个查询出口。
- 同一实际出口 IP、同一服务器、同一 ASN 或同一来源不得占据大部分主力名额。
- 默认目标是同一出口 IP 最多保留 2–3 个，同时尽量覆盖不同协议、运营商和线路。
- 同出口/IP/ASN/来源的硬上限作用于严格主力、`👆手动优先测速` 和自动组；亚洲候补只做排序降权和标记，只有超过 150 总上限时才按质量、历史和多样性共同裁剪，避免再次删除本地可能好用的协议/凭据变体。
- 地区/ASN 查询失败不得破坏整个发布；失败节点应有明确的未知地区策略和诊断。
- 未验证真实出口的模糊名称标签不得单独获得亚洲宽松阈值；名称标签只能作为查询前提示或查询失败时的显式降级证据。

### R7. 面向手动选择的输出

- 正式 GMGN 订阅至少包含：`👆手动优先测速`、`🇭🇰香港`、`🇯🇵日本`、`🇰🇷韩国`、`🇸🇬新加坡`、`🇹🇼台湾`、`🌏亚洲候补`、`🌍非亚洲稳定`、`📦全部入选`。
- 可以保留 `GMGN自动` 作为辅助，但不得把它作为用户主要使用路径。
- `GMGN自动` 只应包含严格稳定层；亚洲候补和观察节点仅进入手动相关分组，避免低置信节点被自动选中。
- `👆手动优先测速` 只包含亚洲核心、亚洲弹性和非亚洲稳定；亚洲候补仍可在五地区组、`🌏亚洲候补` 和 `📦全部入选` 中由用户单独手测。
- 节点名称不得附加每轮变化的延迟、成功率或排名；同一稳定 `candidate_id` 跨运行应保持相同输出名称。
- 主力订阅与更宽的亚洲候选/候补输出边界必须清晰，避免主力被大量 Timeout 节点淹没，也避免用户完全失去本地可能可用的节点。

### R8. 发布安全、兼容和可观测性

- 新方案先以独立 `clash-cn-gmgn-v2-shadow` 分支/订阅影子发布，不直接覆盖旧 `clash-cn-output` 或现有 `clash-cn-gmgn-output`。
- 任一分片、校验、历史状态、配置渲染或 Mihomo 校验失败时，不得覆盖上一版可用订阅。
- 发布状态必须记录来源 SHA、代码 SHA、运行 ID、阈值版本、节点分层数量、地区数量、淘汰原因分布、历史迁移数量、相对 profile path 和逻辑 bundle ID/hash。可原样从 shadow 提升到正式分支的 payload 不得包含分支名或订阅绝对 URL；绝对 URL 只记录在 rollout 证据与用户文档。
- 状态还必须记录 Python/PyYAML/Mihomo 版本与二进制 hash、并发参数、观察窗口、分片出口和策略 schema；`history.json` schema 升级必须有显式迁移或失败关闭路径。
- rollout 分为独立门禁：代码与离线测试完成、单次真实影子验证、连续三次有效影子运行验收、用户确认默认入口迁移。前一阶段通过不自动授权后一阶段覆盖旧订阅。
- 正式迁移必须提升最后一个已验收的同一 V2 bundle，保持 `run_id`、source SHA 和 bundle hash 完全一致，不得在迁移时重新测速或重新选择。
- 文档必须明确列出 GitHub 候选池、旧 gstatic 订阅和 GMGN 正式订阅的用途与正确地址。
- rollout 完成前 gstatic 继续作为回滚对照；完成连续 3 次有效 GMGN 验收后，文档与推荐入口切换到 GMGN，gstatic 分支写入冻结状态和最后更新时间，并移除其自动触发但不破坏旧 URL。
- Clash Verge 更新后应能通过分组名称和状态判断正在使用哪一种订阅。
- 发布前必须使用固定版本/hash 的 Mihomo 校验，发布后必须以防缓存方式重新下载远端状态和配置，校验 schema、hash、数量、分组引用与运行关联。
- 读取上一版状态或输出遇到暂时网络错误、坏 JSON/YAML 或 hash 不一致时必须失败关闭；只有明确确认分支从未存在时才允许首发。

### R9. 性能与容量

- 方案优先通过同一仓库内的快照、分片和并发解决性能问题；只有证据表明单仓库/单流水线受到硬限制时才拆分仓库。
- 运行前估算最坏耗时，避免启动注定超过 CNB 超时限制的任务。
- 在当前约 2000–2500 个候选规模下，目标是完整运行可重复完成，并生成每分片耗时、请求吞吐和错误率诊断。
- 首次调优应以受控候选子集比较多个 workers 档位，依据吞吐、目标对照、Timeout 和 controller 错误率选择一个版本化固定默认值；未经数据证明不得直接把每片并发提升到 32–48，生产运行中的动态自调并发推迟到有充分数据后再评估。
- 发布写入应记录先前分支 tip 并使用等价 compare-and-swap/lease 保护，防止较旧运行覆盖较新结果。
- 增加来源时必须受 CNB 容量预算约束；在现有 4×16 workers、20 轮、3000 ms 请求上限下，候选池接近约 5000 时必须先做受控抽样/去重/扩容评估，而不是等待运行时超预算失败。
- 当前约 2260 个候选、约 24 分钟的真实结果不支持立即拆仓库；只有候选规模持续进入约 8000 以上、单次稳定耗时超过 60 分钟或确认触及 CNB 单仓库硬限制时，才设计主仓库 + 多 Worker 仓库。拆分前必须确认并发额度是按仓库还是按账号计算。
- 若未来拆分，主仓库是唯一候选快照与正式发布者；所有 Worker 必须测试同一来源 SHA 和规则版本，只上传结果，任一 Worker 缺失都不得覆盖上一版订阅，用户订阅 URL 保持不变。

## Acceptance Criteria

- [ ] 固定来源快照中的每个候选在正式 GMGN 运行中恰好产生 20 次采样结果，并通过跨分片完整性校验。
- [ ] GitHub 候选池在单个来源失败、某一亚洲地区归零或 previous 状态暂时不可读时保持 last-good，不发布异常缩水版；恢复后能自动重新纳入来源。
- [ ] provenance sidecar 能按公开 HMAC `candidate_id` 回答节点来自哪些仓库/订阅、首次/最后见到时间、地区证据和 GitHub 实测状态；裸 fingerprint、原始私有订阅 URL 和可枚举端点/出口标识均不会进入公开产物。
- [ ] GitHub/CNB 使用固定 identity test vector 证明四类 HMAC ID 完全一致；key/version/epoch 任一不一致会在候选发布或 probe 前失败关闭。
- [ ] `<=1000 ms`、慢响应、Timeout/无结果及主要错误类别能在节点级私有记录和安全的公开诊断中被验证。
- [ ] 亚洲节点一次差评只发生状态降级；连续运行历史达到配置门槛后才从候补移除，恢复后能自动晋级。
- [ ] 新亚洲节点本轮至少一次 GMGN 响应即可进入仅供手动使用的亚洲候补；新节点 20 轮完全无响应不会进入 CNB 正式订阅，历史候补则按连续 3 次有效坏运行保护。
- [ ] 来源暂时抓取失败、GMGN/runner 系统异常或被拒绝发布的运行不会删除节点、不会增加 bad-run streak，也不会覆盖与上一版 profile 对应的诊断。
- [ ] 主力不足 80 时仍可安全发布且不会自动放宽质量阈值；总数永不超过 150，非亚洲永不超过 20。
- [ ] 最终配置包含要求的手动、地区、候补、非亚洲和全部入选分组，且所有引用均通过 Mihomo 配置校验。
- [ ] 同一出口/服务器/ASN/来源的集中度受到可测试限制，未知出口有明确降级行为。
- [ ] 多样性硬上限不会无条件删除亚洲候补中的可用协议/凭据变体；主力与候补分别有可测试的硬限制和排序降权规则。
- [ ] 用户刷新正确 GMGN 订阅后不会再看到旧 `automatic / 84` 作为新方案结果；文档和状态能明确识别订阅类型。
- [ ] 连续 3 次有效 GMGN 验收通过后，gstatic 自动任务停止，`clash-cn-output` 保留最后一版且明确显示冻结/旧版状态；GMGN 长期异常时可通过受控手动操作恢复。
- [ ] 至少完成一次不覆盖旧默认订阅的真实 CNB 影子运行，并核对节点分布、错误率、四分片一致性和历史迁移结果。
- [ ] 至少连续完成三次不同 source SHA、相邻至少 21600 秒的 accepted 影子运行，验证真实跨运行名称、地区、history 与 bundle 关联；再用不进入用户订阅的确定性 canary/replay 证明 `bad1 → bad2 → bad3/remove → recovered`、重复 SHA 和无效运行不计数。任一正式输出都能找到对应的保留诊断。
- [ ] 20 轮采样带可验证时间戳并覆盖配置化最短观察窗口；并发基准证明所选 workers 档位没有用显著增加的假 Timeout 换取表面速度。
- [ ] 每个新 GitHub profile SHA 自动触发一次 GMGN 20 轮；同 SHA 重试、失败运行或短时间重复事件不会重复增加 bad-run streak，任务不会因并发覆盖较新的运行。
- [ ] 自动化测试覆盖统计、阈值边界、历史状态迁移、多样性、名称稳定、地区分组、脱敏、来源新鲜度和发布回滚。
- [ ] 自动化发布后 smoke 会重新读取 GitHub/CNB 远端产物，验证 schema、SHA-256、节点数、分组引用、20 轮/四分片关联和 Mihomo 可加载性。
- [ ] V2 影子 profile、status、`history.json` 与 current diagnostics 在同一 bundle/提交中共享 `run_id`、source SHA 和 bundle hash；拒绝运行不覆盖 V2 shadow last-good。
- [ ] 用户批准迁移后，正式 GMGN 远端回读内容与最后一个连续三次验收通过的 V2 bundle 完全一致，迁移过程没有重新测速或重新选择。
- [ ] 不可信外部配置在启动前经过公网地址固定与二次校验，并在版本化 network guard 隔离中运行；guard 不可用、DNS 固定结果漂移或私网/云元数据阻断自检失败时不启动分片。探测 job 无发布凭据，公开 provenance/diagnostics 不包含私有订阅 URL、token 或可逆凭据。
- [ ] 四个分片的实际出口和 canary 结果满足可比性门槛；任一分片明显偏离时，本轮不排名、不增加 bad-run streak、不覆盖 last-good。
- [ ] Trellis 任务在实施前加载 aggregator 根项目的真实编码/测试规范，而不是误用 `manager` 子模块规范。
- [ ] 至少完成一个外部亚洲源的边际增益评估与受控接入；优先验证小而更新活跃的来源，超大 reservoir 必须有每源/每地区/每入口限额和与现池重叠门禁。

## Out of Scope

- 保证任意节点在所有用户网络、所有时间都低于 1000 ms。
- 用 CNB 测速替代用户在 Clash Verge 中的最终实时手动选择。
- 为达到固定数量把亚洲手动候补冒充严格主力，或自动降低核心/弹性/非亚洲质量门槛。
- 在没有性能证据时拆分成多个 GitHub/CNB 仓库。
- 在规划阶段修改业务代码或切换用户当前默认订阅。
- 为提高速度而让同一节点的多轮同时执行，或让正式候选产生少于 20 次观测。
